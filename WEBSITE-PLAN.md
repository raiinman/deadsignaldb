# Dead Signal DB Website Plan

## Goal

Make `deadsignaldb.com` feel like a real parent brand and public operating archive, not a landing page wearing the visual language of Once Human.

## Primary navigation

- `FIELD` — interactive project overview.
- `PROJECTS` — complete project index.
- `TRANSMISSIONS` — updates and releases.
- `ARCHIVE` — inactive and completed work.
- `ABOUT` — identity, principles, and authorship.

## Project records

Every project record should contain:

- name and one-line identity
- status
- type or medium
- current state
- platform or access point
- technology, when useful
- start or release date, when useful
- entry link
- optional development notes

The shared record structure creates coherence while leaving each project free to be itself.

## Status model

Use `ACTIVE`, `LIVE`, `DEVELOPING`, `EXPERIMENTAL`, `PAUSED`, and `ARCHIVED`. Use “coming soon” only when a public commitment exists.

## Homepage behavior

The homepage should begin with a clear Dead Signal DB identity, then introduce The Signal Field. It should also provide a conventional list/index view so users are never dependent on animation or discovery mechanics.

## Technical principles

- Projects stay in separate repositories.
- The portal must remain technology-agnostic.
- Project links should support both subdomains and external destinations.
- Data should be registry-driven so adding a project does not require redesigning the page.
- Motion must respect reduced-motion preferences.
- Every interactive view needs a usable keyboard and static fallback.
- Public metadata should describe the parent brand independently from any one project.

## Release phases

1. Lock brand language and project taxonomy.
2. Replace the temporary portal with the brand shell and navigation.
3. Build The Signal Field with an accessible index mode.
4. Add project records for Wakeframe and Once Human.
5. Add transmissions and archive content models.
6. Add richer interaction only after the structure is useful without it.
